# 0021 — Rebuild the COBOL gates on Windows from unmodified source

Date: 2026-08-16
Status: Accepted

## Context

Four COBOL gates carried forward from Ag3nt24 v1.0.0 into `prior-art/a24-v1/kernel/` (was `from-old-ag3nt24/kernel/` in the private kernel repo): `tenet_gate`, `provenance_validate`, `rune_authorize` and `rune_rotation`. Each arrived as a `.cbl` source and a compiled `.bin`.

The `.bin` files are Linux x86-64 ELF executables dynamically linked against glibc. The target for the rebuild is Windows, WSL is not installed and is not to be used, and Docker and Linux VMs are equally out. The carried binaries therefore cannot execute here at all. They are evidence that the old build happened, not a runnable kernel.

That leaves the source. Canon already rules that the kernel ports as source rather than being re-derived, and that the five end-to-end scenarios port with it as a conformance gate — a changed verdict means the port is wrong and stops. What canon does not settle is the baseline: recompiling the same source on Windows reproduces the same *source*, not the same *binary*, so "identical verdicts" has to be measured against something other than the original binaries' observed output, which is unobtainable without the Linux box the ruling excludes.

## Decision

Recompile all four gates on Windows from byte-identical copies of the carried `.cbl` sources, and prove the port with a conformance suite whose expectations are derived by reading the COBOL.

The sources are copied into `kernel/` and verified by sha256 against `prior-art/a24-v1/kernel/` (was `from-old-ag3nt24/kernel/` in the private kernel repo). Nothing in them is edited — not logic, not comments, not whitespace, not the `PROGRAM-ID`. GnuCOBOL 3.2.0 compiles all four unmodified with `cobc -x`; only warnings are emitted, so no compile fix was needed and none was made. Had one been needed it would have been escalated rather than applied, because changing the source to make it build is a decision about the kernel's meaning.

Compiled output is not committed. `kernel/bin/` is gitignored except for `BUILD-MANIFEST.json`, which records per gate the source filename and sha256, the output filename and sha256, and the full `cobc --version` string. The binary is reproducible from the manifest; carrying it would repeat the mistake the Linux `.bin` files represent.

The JS bridges port with exactly one change each: the binary path moves from `kernel/<name>.bin` to `kernel/bin/<name>.exe`. The fixed-width record formatters are untouched, because those formatters are the interface contract with the COBOL `PIC` layouts and a single character of drift in them changes verdicts silently.

Two Windows toolchain facts are handled in `scripts/build-kernel.js` rather than left to ambient environment. Outside an MSYS2 shell `cobc` resolves its configuration to an MSYS-style path Windows cannot open, so the build derives `COB_CONFIG_DIR` and `COB_COPY_DIR` from the location of `cobc` itself. And the compiled gates link against `libcob` and the C runtime DLLs beside the compiler, which Windows resolves from `PATH` rather than from the executable's own directory; that directory is recorded in the manifest and the conformance runner puts it on `PATH` and probes a gate before reading any verdict. A gate that fails to start returns no verdict, and a missing verdict compared against a pinned one reads as "the port is wrong" when it is really "the runtime is not on PATH" — a misdiagnosis this suite cannot afford to make.

## Consequences

The conformance suite is now the thing that proves verdicts unchanged. That is the whole weight-bearing claim of this phase, and it is worth being precise about what it establishes. A source-derived expectation is reviewable in a way an opaque binary never was: `conformance/expected.json` carries a `why` string next to every pinned verdict, tracing it to specific lines of the gate. Anyone can check the reasoning. The gates are short, straight-line boolean logic with no I/O, no clock and no randomness, which is why the reading is tractable at all — `rune_rotation` reads its epoch day as input rather than from the system clock, so a conformance run is reproducible on any day.

For `rune_rotation` the baseline is stronger than source-derived, and this was not expected. The v1.0.0 repo still exists on disk with its generated `out/` fixtures intact — the rune tables written by the *original Linux* `rune_rotation.bin` — and the seed that produced them is a literal in that repo's rotation tests. Given that seed, the rebuilt Windows gate reproduces both days' tables byte-identically, signature lines included. That is a captured-baseline match against the original binary's observed output, which is exactly the evidence the handoff brief's first open question asked for and assumed was unobtainable without a Linux box. It settles that question for the rotation gate specifically: the Windows rebuild is observationally identical to the Linux original, not merely faithful to a reading of the source. The other three gates remain source-derived, since no captured output of theirs survived.

The suite catches the failure mode that matters. `tenet_gate` evaluates all five tenets unconditionally and each failing tenet overwrites a single `DENIAL-REASON` field, so when several fail the *last* one in source order owns the reported reason. A reimplementation reporting the first failure instead would still return DENY and would still look correct. Pinning the exact reason string is what makes that drift visible, and scenarios B and C exercise it directly.

Two costs are now on the books. GnuCOBOL 3.2.0 is a build dependency of the repo on every developer machine, and the manifest pins the version because a different compiler is a different experiment. Separately, `rune_rotation.cbl` compiles with `value size exceeds data size` warnings on `LCG-A` and `LCG-M`: both constants are ten digits declared into `PIC 9(9)` fields and are truncated. That is the carried source's own behaviour and is not to be corrected here — but it means the rotation PRNG is not the textbook LCG its comments describe, and anyone reasoning about rotation from those comments will be wrong.

Building the suite also found a real defect in the carried scenarios, which is the kind of thing a conformance gate is supposed to earn its keep by finding. Scenarios A and D step 0 request capability 9 for rune 1 on epoch day 20260112, and that pair authorizes against no table the kernel has ever produced. The v1.0.0 git history explains it exactly. Commit `5f9de4b` checked in the day-1 table as a uniform +8 cyclic shift — rune n to capability n+8, so rune 1 held capability 9 — in the very commit that first introduced `rune_rotation.cbl`. That table was a hand-written placeholder that was never regenerated from the kernel shipping beside it. Commit `959bd59`, the v1.0.0 freeze, replaced it with genuine rotation output in which rune 1 holds capability 23. The scenarios were not updated, and nothing caught it because the scenario runner was never re-run after the freeze — `docs/Testing, Validation, and Results.md` records scenario A as ALLOW, and that record predates the change that invalidated it.

The correction moves the requested capability from 9 to 23 and holds the actor at rune 1, since rotation is the capability moving between runes. `(3, 9)` would satisfy both days equally well and was rejected only because it changes which actor the scenario is about. The archive is not edited: `conformance/run.js` applies the correction at load time, asserts the archive still contains the value it expects to replace, and prints the substitution on every run, so the divergence between the archive and what executes stays visible instead of turning into folklore. With it the suite reports 33 of 33 checks and 5 of 5 scenarios.

The lesson generalises past this one pair. A fixture that is checked in rather than generated will drift from the kernel that is supposed to produce it, and without a runner that executes end to end, the drift is invisible for months — here, from January to the July freeze and past it. The conformance suite is the standing answer to that, which is why it regenerates its rune tables from the kernel on every run rather than committing them.
